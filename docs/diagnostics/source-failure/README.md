# 无需 recent-id 的只读排查

这组请求来自用户提供的失败记录，仅用于排查，不是部署包或完整业务报告。
三个 JSON 文件都是 `execute_eql` 的参数对象；逐个执行，保留完整请求和响应。
不要把三份 JSON 合并成一次调用。已按本地 EDN 核对输入集合和输出属性；尚未在线执行。

共同设置 `retain_result=false`，目的是直接观察源查询响应，减少本轮对 handle 读取链路的依赖。
须先确认实际工具支持这个值；宿主仍可能裁剪或保留结果。预览不完整时只能用于诊断，
不能据此输出完整 ETA 数量。不要猜测 handle；请求与返回关联异常时隔离该次结果。

1. `01-current-code.json`：US Vendor64342，旧接口的合法 VENDOR_CODE / COUNTRY_ALL。
   相比原失败记录，同时纠正两个已确认不支持的参数，并限定单 Vendor。
   用于检查当前明细路径是否至少能返回数据；不提供 Code×Source 联合分布。
   若成功，只能说明该路径可用，不能证明 V3 所依赖的其他对象可用。
   若空，仍需排查实际数据、权限、Country/ID 和结果关联，不等于 PastDue=0。
2. `02-explore-v2.json`：先确认线上存在 explore-v2-query/rows，再执行。
   与失败 V3 保持同一 US13 Vendor、CURRENT、联合粒度、分母和无 Top N 限制。
   使用 v2 的22输入，没有 v3 选择/展开新增项。本例无排名或桶筛选，因此该 v2
   测量路径适用于排查所需联合分布，但没有 v3 的 SELECTION 记录。
3. `03-explore-v3.json`：原失败 V3 查询，仅将 retain_result 改为 false。
   若原 retain=true 失败而此请求成功，可进一步排查保留结果路径；因两次执行不在
   同一时刻，仍须排除暂时性故障，不能直接认定根因。

结果判读：

| 现象 | 下一步 |
|---|---|
| 旧接口成功，v2成功，v3失败 | 优先核对线上 V3 SQL、绑定、部署版本与引擎兼容；不能归为全源故障。 |
| 旧接口成功，v2和v3失败 | 优先查 explore 共用 SQL、附加依赖、类型、权限与参数绑定。 |
| 三者均报源错误 | 检查共同依赖/连接，但不同错误仍可能独立；需要更底层的错误信息。 |
| 非保留请求返回事实，后续保留读取为空或串号 | 隔离保留/关联链路；事实仍须核对完整性和范围。 |

若只能看到通用源错误，可由 IT 使用受控只读连接执行线上实际绑定的 SELECT，
或运行 EXPLAIN，取得原始数据库异常、引擎/JDBC版本和参数类型。凭据不写进文件。
不要把本地 chdb 通过视作线上 JDBC 已通过。仅缩减 EQL 输出列或 page-size 不保证
简化底层 SQL 的聚合成本。

先跑第1项；成功再按第2、3项对照。每项执行一次，失败后不要重复相同请求。
三项不是严格单变量实验；有了响应后再对故障路径作单变量缩减。
