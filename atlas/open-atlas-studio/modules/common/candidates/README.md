# common/candidates — 机器提议

## 它回答一个问题，而且只回答一个

**「这几列名字一样，可能是一回事。」**

它**不**回答「这个概念叫什么」——那句话机器说不出口，因为它手上只有历史字段名，而
[D2.26](../../../docs/design/20-dialect.md#d226-词条glossary-的机制本体) 恰恰禁止拿历史
字段名当概念名。所以按名字频次聚类出的候选，`:term` 一律是 `nil`，挂一条
`:id-required-from-owner true`。

这就是**机器提议 / owner 处置**那条分界，也是 D2.26「同名 ≠ 同义」唯一的执行机制。

## 为什么单独一个模块

立它的时候有**两个**调用方：

| 调用方 | 从哪里挖 | 今天 |
|---|---|---|
| B2 的一次性转换器 | 语料转换的产物 | **已退休**（2026-08-24，见 [fixtures/demo](../../../fixtures/demo/README.md)） |
| B4 的池 | 池里的内容 | 唯一调用方 |

当年的论证是「两份实现总有一天分叉」，而这里分叉尤其贵：**同一份模型在两条路上会
得到不同的候选**，而候选是 owner 逐条过目的东西（S5.4）——他会以为自己看的是全部。
转换器退休后这条论证没有了第二个调用方撑着，**照实说**：现在只剩池。

它仍然留在 `common`，理由换成了依赖方向——池是 studio，本模块是 common，
[D1.8](../../../docs/design/10-platform-boundary.md) 不许 common 反过来依赖 studio。
与 [toolkit](../toolkit)、[search](../search) 同则。

## 只做提议，不做处置

签字文件的解析、合并与拒绝**留在调用方**——B4 是 `confirm_candidates` action
（B2 当年是 `signoff.edn`）。

提议是机器的活，处置是人的活。两者住在一起，迟早有人顺手让它们互相看一眼——B2 已经
拒绝过一次这样的提案（「让候选回头看 `additions/`」，理由是 **等于让 owner 签自己
刚写的东西，分离就成了走过场**；当年的实现与论证在
`git log -- modules/legacy-import` 里）。

## B4.4 的裁定

### ① 池里的候选从**池**挖，不从别处

池是活的模型：新属性经 action 进来，不经转换。候选因此读池。

**「机器提议 / owner 处置」在池里依然成立**，只是形状变了：机器提议的是**结构事实**
（这个本地名在 5 个 entity 上重名且类型兼容），owner 裁的是**意义**。没有人手写那份
聚类——分离是真的。

### ② 确认记录是**不可变**的，而且**不进模型**

B2 时代的「签了就不能改」是我说错的话：`apply-signoff` 是纯函数，没有历史
（那次更正当年写在 `fixtures/b2/signoff/README.md`，随语料一并删除，见
`git log -- fixtures/b2`）。池有事务，所以这一次它可以是真的。

确认记录是池里一种**独立的实体**，**不出现在 `as-dialect` 的产物里**——它是治理痕迹,
不是模型内容。混进去会让同一个模型因为「谁签的」不同而产出不同的 content-hash,
而制品的身份必须只由模型决定（[D4.3](../../../docs/design/40-artifacts.md)）。

记录至少带：候选的身份、裁决、产出的对象、**入口**（ui/http/mcp）、**前后 revision**。
入口那一项是 principles「存储与同步」点名要的——「才答得出**这个 revision 里哪些改动
来自 AI**」。

### ③ 「未签字的候选不写入模型」在池里的准确说法

B2 里这条靠 `apply-signoff` 只合并签过的候选。池里**写面是 action**，没有那道合并。
所以这条规则的准确形态是：

> **由候选派生的绑定，必须经签字通道产生。** 作者直接写一条词条绑定仍然合法
> （B2 的 `:authored-terms` 就是这条路），但它在 provenance 上**与签字派生的分得开**。

价值在于分得开：一条绑定是「机器提议、人核准」还是「人直接写的」，是两件不同的事,
而报告与审计都要答得出是哪一件。**把两者混成一样，签字就退化成一次多余的点击。**
